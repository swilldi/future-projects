# Спецификация

## Одним абзацем

Сервер фактов с версионированием. Каждое изменение факта получает новую ревизию. Клиент помнит последнюю ревизию и просит только изменения. Чтение публичное с кэшированием, запись по токену.

## API

| Метод и путь | Параметры | Ответ | Ошибки |
|---|---|---|---|
| `GET /v1/facts/{MM-DD}` | заголовок `If-None-Match` | `200 {"date","facts":[...],"revision"}` с `ETag`, или `304` | 400 неверная дата |
| `GET /v1/facts/random` | `?date=MM-DD`, без даты сегодня по UTC | `200 {fact}` | 404 нет фактов на дату |
| `GET /v1/facts` | `?since=N&limit=1000` | `200 {"facts":[...],"deleted":["id"],"revision":M,"hasMore":bool}` | 400 |
| `POST /v1/facts` | токен, тело факта без `id` | `201 {fact}` | 401, 400 |
| `PUT /v1/facts/{id}` | токен, тело | `200 {fact}` | 401, 404, 400 |
| `DELETE /v1/facts/{id}` | токен | `204` | 401, 404 |
| `GET /healthz` | | `200` | 503 |

Факт:

```
{ "id": "09-03-1", "monthDay": "09-03", "year": 1939, "text": "...", "source": "Википедия",
  "sourceURL": "https://...", "revision": 42, "updatedAt": "..." }
```

Ошибки в JSON как в сокращалке. Токен в заголовке `Authorization: Bearer <token>`.

## Дельта

- `since=0` отдаёт всё живое и без удалённых: первая синхронизация.
- `since=N` отдаёт записи с `revision > N`: живые в `facts`, удалённые в `deleted` по `id`.
- Порядок по ревизии, `limit` по умолчанию 1000, `hasMore` и клиент повторяет с `since=revision` из ответа.
- `revision` в ответе это максимальная ревизия среди возвращённых записей или текущая максимальная в базе, если записей нет.

## ETag

- Для `GET /v1/facts/{MM-DD}`: `"<maxRevisionНаДату>-<count>"`. Слабый ETag не нужен.
- `If-None-Match` совпал: `304` без тела, `ETag` в ответе.
- `Cache-Control: public, max-age=3600` на чтение по дате.

## Импорт

`factsctl import facts.json --database-url ...`: читает файл сборщика, для каждого факта `INSERT ... ON CONFLICT (id) DO UPDATE` только если текст или источник изменились. Неизменившиеся не получают новую ревизию. Факты из базы, которых нет в файле, не трогаются. Печатает: добавлено, обновлено, без изменений.

## Хранение

```
facts
  id TEXT PRIMARY KEY
  month_day CHAR(5) NOT NULL
  year INT
  text TEXT NOT NULL
  source TEXT NOT NULL
  source_url TEXT
  revision BIGINT NOT NULL              -- из последовательности facts_revision_seq
  updated_at TIMESTAMPTZ NOT NULL
  deleted_at TIMESTAMPTZ
индексы: (month_day) WHERE deleted_at IS NULL; (revision)
```

Ревизия: `nextval('facts_revision_seq')` в триггере `BEFORE INSERT OR UPDATE`, чтобы приложение не могло забыть.

## Защита записи

- Токен из `ADMIN_TOKEN`, сравнение постоянного времени.
- Ограничение: 10 неудачных попыток в минуту с одного IP, дальше 429.
- Без токена в окружении запись отключена: 503 на запись.

## Клиент в календаре

- `RemoteFactRepository` реализует тот же `FactRepository` через локальное хранилище фактов: SQLite через GRDB или JSON-файл с индексом. Выбрать GRDB: база уже большая.
- При запуске в фоне: `GET /v1/facts?since=<локальная ревизия>`, слияние: upsert по `id` если ревизия больше, удаление по `deleted`. Сохранить ревизию.
- Первая синхронизация с `since=0` заменяет бандл.
- Бандл остаётся как запасной: если локальная база пуста и сети нет, факты из бандла.
- `If-None-Match` для запроса на дату не нужен клиенту: он ходит только за дельтой. Записано.

## Границы

- Ревизия обгоняет из-за отката транзакции: пропуски в номерах допустимы, клиент сравнивает `>`.
- Одновременные две правки одного факта: последняя побеждает, обе получают ревизии.
- Дельта с `since` больше текущей: пустой ответ, `revision` текущая.
- Импорт того же файла дважды: ноль обновлений.
- Дата `02-30`: 400.
- Клиент получил `hasMore`, но сеть оборвалась: следующий запуск продолжит с сохранённой ревизии, ничего не потеряно.

- Пуш-уведомления об обновлениях.
- Языки сверх русского.
- Модерацию.
