# CLAUDE.md

Инструмент для iPhone и iPad: экран это восемь струн, в покое они колышутся волной, при касании выпрямляются и играют. Звук синтезируется, картинка на Metal, отдача в палец. Подробности в `docs/`.

## Роли

Код в этом проекте пишет автор сам, руками, ради практики. Ты нужен для двух вещей.

1. **Ревью.** Проверять написанное по `docs/REVIEW.md` и сверять с `docs/ARCHITECTURE.md`. Находить проблему, объяснять, почему это проблема, и одной строкой, как бы исправил. Не переписывать код. Не предлагать «давай я сделаю».
2. **Рутина.** Когда автор явно просит размножить однотипный код: повторять существующий образец из проекта буква в букву по стилю, не выходить за рамки задачи, не трогать соседний код, не улучшать попутно.

Если задача не попадает ни в одну из ролей, спроси, прежде чем писать код.

## Куда смотреть за контекстом

- `docs/SPEC.md`: что должно быть сделано и чего не должно.
- `docs/ARCHITECTURE.md`: как разложен код и почему. Отклонение от него это замечание на ревью.
- `docs/REVIEW.md`: чеклист ревью, идти сверху вниз.
- `docs/PLAN.md`: на какой фазе проект. Не проверять то, что ещё не должно быть сделано.
- `docs/NOTES.md`: решения и открытые вопросы автора.

## Формат отчёта ревью

Список замечаний по убыванию важности. Каждое: уровень (блокер, важно, мелочь), файл и строка, что не так, почему это проблема, как исправить в одну строку. В конце три строки: что сделано хорошо, что проверить руками, что не проверял. Без пересказа кода и без общих советов.

## Правила кода

- Swift 6, strict concurrency включён.
- SwiftUI везде. UIKit только через представимые обёртки, если SwiftUI физически не умеет, и это отмечено комментарием.
- Observation (`@Observable`), не `ObservableObject`.
- Форматирование: swift-format с конфигом из репозитория. Со стилем не спорить.
- Без `!` и `try!` вне тестов. Без `DispatchQueue`, только async/await и `@MainActor`. Исключения перечислены в правилах проекта.
- Именование: типы `UpperCamelCase`, остальное `lowerCamelCase`, без сокращений. Файл называется как главный тип в нём.
- Один тип на файл, кроме маленьких вспомогательных.
- Тесты на Swift Testing. Имя теста описывает поведение.

## Правила проекта

- Четыре пакета с границами по потокам: `StringsCore` (музыка, физика, пресеты; чистый, без UI и аудио), `StringsAudio` (DSP и движок; аудиопоток), `StringsRender` (Metal; главный поток в `draw`), приложение (ввод, отклик, состояние, экраны). Импорт против направления это блокер.
- Аудиопоток по правилам аудио-песочницы: без аллокаций, блокировок, `await`, ARC-трафика. Команды только через lock-free очередь.
- Кадр на главном потоке укладывается в 8 мс: физика, сборка буферов, энкодинг. Аллокации в кадре запрещены.
- Пресет это структура данных в `StringsCore`. Ветвление по имени пресета в коде это нарушение.
- Ввод только через один `UIView` с `touchesBegan` и родственниками. SwiftUI-жесты для струн не использовать: они не дают надёжного мультитача.
- Каждая подсистема тестируется без остальных: физика на массивах, синтез на массивах, музыка на числах, состояние на событиях.
