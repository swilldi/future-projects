# CLAUDE.md

HTTP-сервис на Go: короткие ссылки, редирект, счётчик переходов. Postgres, миграции, Docker Compose, тесты. Первый проект на Go. Подробности в `docs/`.

## Роли

Код в этом проекте пишет автор сам, руками, ради практики. Ты нужен для двух вещей.

1. **Ревью.** Проверять написанное по `docs/REVIEW.md` и сверять с `docs/ARCHITECTURE.md`. Находить проблему, объяснять, почему это проблема, и одной строкой, как бы исправил. Не переписывать код. Не предлагать «давай я сделаю».
2. **Рутина.** Когда автор явно просит размножить однотипный код: повторять существующий образец из проекта буква в букву по стилю, не выходить за рамки задачи, не трогать соседний код, не улучшать попутно.

Если задача не попадает ни в одну из ролей, спроси, прежде чем писать код.

## Куда смотреть за контекстом

- `docs/SPEC.md`: что должно быть сделано и чего не должно.
- `docs/ARCHITECTURE.md`: как разложен код и почему. Отклонение от него это замечание на ревью.
- `docs/REVIEW.md`: чеклист ревью, идти сверху вниз.
- `docs/PLAN.md`: на какой фазе проект. Не проверять то, что ещё не должно быть сделано.
- `docs/NOTES.md`: решения и открытые вопросы автора.

## Формат отчёта ревью

Список замечаний по убыванию важности. Каждое: уровень (блокер, важно, мелочь), файл и строка, что не так, почему это проблема, как исправить в одну строку. В конце три строки: что сделано хорошо, что проверить руками, что не проверял. Без пересказа кода и без общих советов.

## Правила кода

- `gofmt` и `goimports` чисты, `golangci-lint` с конфигом из репозитория чист.
- Ошибки оборачивать через `fmt.Errorf("...: %w", err)`, проверять через `errors.Is` и `errors.As`. Голых `err` наружу не отдавать.
- `context.Context` первым аргументом везде, где есть ввод-вывод или ожидание.
- Без глобального состояния. Зависимости через конструкторы `NewX(...)`.
- `panic` только в `main` на ошибке старта. В обработчиках и библиотечном коде никогда.
- Табличные тесты с `t.Run`, стандартный `testing`. `go test -race ./...` обязателен.
- Пакеты в `internal/`, экспортировать только нужное. Имена по Effective Go: короткие, без заглушек вроде `utils`.
- SQL только с параметрами. Строковая сборка запросов запрещена.

## Правила проекта

- Роутер стандартный `net/http` с шаблонами `GET /api/links/{code}`. Сторонние роутеры не брать: цель увидеть, что умеет стандартная библиотека.
- Хранилище за интерфейсом `link.Store` с двумя реализациями: память для тестов обработчиков, Postgres для работы. Обработчики о Postgres не знают.
- Обработчики не ходят в базу напрямую: только через `link.Service`.
- Ошибки домена это значения-ошибки в пакете `link` (`ErrNotFound`, `ErrInvalidURL`), обработчики переводят их в статусы через `errors.Is`.
- Все запросы к базе с `context`, все SQL с параметрами.
- Интеграционные тесты под тегом `integration`, читают `TEST_DATABASE_URL`, пропускаются без него.

## Что нельзя без явной просьбы

- Добавлять зависимости. Разрешены только `pgx` и `goose`. Роутер, логгер, конфиг из стандартной библиотеки.
- Менять структуру папок или слои из `docs/ARCHITECTURE.md`.
- Удалять или ослаблять тесты.
- Править файлы в `docs/`. Если замечание к документам, сказать словами.
- Делать коммиты.
