# CLAUDE.md

Общий холст 100 на 100, где все одновременно ставят пиксели. Сервер на Swift через Vapor с WebSocket и Fluent, клиент на iOS, общий пакет моделей, Docker. Подробности в `docs/`.

## Роли

Код в этом проекте пишет автор сам, руками, ради практики. Ты нужен для двух вещей.

1. **Ревью.** Проверять написанное по `docs/REVIEW.md` и сверять с `docs/ARCHITECTURE.md`. Находить проблему, объяснять, почему это проблема, и одной строкой, как бы исправил. Не переписывать код. Не предлагать «давай я сделаю».
2. **Рутина.** Когда автор явно просит размножить однотипный код: повторять существующий образец из проекта буква в букву по стилю, не выходить за рамки задачи, не трогать соседний код, не улучшать попутно.

Если задача не попадает ни в одну из ролей, спроси, прежде чем писать код.

## Куда смотреть за контекстом

- `docs/SPEC.md`: что должно быть сделано и чего не должно.
- `docs/ARCHITECTURE.md`: как разложен код и почему. Отклонение от него это замечание на ревью.
- `docs/REVIEW.md`: чеклист ревью, идти сверху вниз.
- `docs/PLAN.md`: на какой фазе проект. Не проверять то, что ещё не должно быть сделано.
- `docs/NOTES.md`: решения и открытые вопросы автора.

## Формат отчёта ревью

Список замечаний по убыванию важности. Каждое: уровень (блокер, важно, мелочь), файл и строка, что не так, почему это проблема, как исправить в одну строку. В конце три строки: что сделано хорошо, что проверить руками, что не проверял. Без пересказа кода и без общих советов.

## Правила кода

- Swift 6, strict concurrency включён. Пакет собирается на macOS и Linux.
- Не использовать API, которых нет в Foundation на Linux. Проверка: сборка в Docker с образом `swift`.
- Публичный API документирован комментариями `///`, остальное `internal` по умолчанию.
- Форматирование: swift-format с конфигом из репозитория.
- Без `!` и `try!` вне тестов. Без `DispatchQueue`.
- Именование: типы `UpperCamelCase`, остальное `lowerCamelCase`, без сокращений.
- Тесты на Swift Testing. Тесты не ходят в сеть и не зависят от часов.

## Правила проекта

- Сообщения только из `PixelShared`. Дублирование структуры сообщения на сервере или клиенте это блокер.
- Состояние доски и соединения живут в акторах. Прямой доступ к массиву пикселей из обработчика это нарушение.
- Задержка между пикселями проверяется на сервере по идентификатору клиента. Клиентская проверка только для интерфейса.
- Каждый вход валидируется: координаты в границах, цвет из палитры, идентификатор клиента формата UUID. Невалидное сообщение закрывает соединение с кодом.
- Запись событий в базу пачками, снимок доски раз в минуту. Синхронная запись на каждый пиксель это нарушение.

## Что нельзя без явной просьбы

- Добавлять зависимости. Сервер: Vapor и Fluent с драйвером Postgres. Клиент и общий пакет: ноль.
- Менять структуру папок или слои из `docs/ARCHITECTURE.md`.
- Удалять или ослаблять тесты.
- Править файлы в `docs/`. Если замечание к документам, сказать словами.
- Делать коммиты.
